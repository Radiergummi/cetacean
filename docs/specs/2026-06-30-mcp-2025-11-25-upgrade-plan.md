## Summary

The MCP server was built against the `2025-06-18` profile. Two spec revisions have since shipped: `2025-11-25`
(final, current stable) and the `2026-07-28` release candidate ("MCP 2.0", finalizing ~2026-07-28). The pinned
`mark3labs/mcp-go` v0.54.0 already tracks `2025-11-25` as its latest negotiated version and exposes the relevant
APIs, so this batch needs **no dependency bump**.

This plan covers every `2025-11-25` feature that mcp-go v0.54.0 supports today and that serves the product goal —
giving AI agents *precise insights* and *safe, ACL-gated changes*. Anything gated on the `2026-07-28` finalization or
absent from mcp-go is deferred to tracked issues (see [Deferred](#deferred-tracked-as-issues)).

## Goals

- Agents get machine-parseable, schema-described tool results instead of opaque JSON-in-text.
- The server tells agents how to use it (usage contract, per-tool semantics).
- Authorization discovery works with OIDC-aware clients.
- The streamable endpoint rejects forged `Origin` headers (DNS-rebinding defense).
- Long-running mutations can report progress and be polled/cancelled (experimental).

## Non-goals

- The `2026-07-28` stateless protocol core, MCP Apps, and the reshaped Tasks lifecycle. Tracked as issues; revisit
  when the spec finalizes and mcp-go ships support.
- Replacing the in-memory OAuth/session store. Tracked as an issue.

## Phase 1 — Structured tool output + output schemas — **DONE** (`77b75c7`)

> **Implemented — read this before touching tool output.** The final shape deviated from the sketch below; the
> sketch is kept for context. What actually shipped:
>
> - **No handler-signature change.** Handlers still return `(string, error)` via `marshalResult`. A new
>   `structuredToolResult(text string)` helper (`internal/mcp/tools.go`) parses that JSON string into a
>   `map[string]any` and wraps it with `mcplib.NewToolResultStructured(obj, text)` — structured content for
>   `2025-06-18`+ clients, text fallback for older ones. If the text is not a JSON object it degrades to text-only.
>   This avoided churning ~20 handlers and the shared `updateServiceHandler`/`removeHandler` factories, and kept all
>   existing `td.handler` unit tests valid. The per-tool result-type sketch (`ServiceMutationResult`, etc.) was
>   **not** built — unnecessary given the parse-the-JSON approach.
> - **Curated output schemas only.** Per the validation decision (below), schemas are attached to the tools whose
>   shape we own: `search` → `cluster.SearchResults`, `get_logs` → `LogResourceResponse`, and every `remove_*` →
>   a new `removalResult{Removed bool}` type. Docker-passthrough mutations (`scale_service`, `update_service_*`,
>   node tools) carry **no** schema and return raw `swarm.*` as structured content.
> - **Validation is enabled server-wide.** `mcpserver.WithOutputSchemaValidation()` is set in
>   `internal/mcp/server.go`. It only bites tools that declare a schema. Verified empirically (`output_schema_test.go`,
>   `TestCuratedToolOutputsValidate`) that the auto-derived schemas accept real handler output — **the `omitempty`
>   trap I worried about (Cursor/Attrs/Detail/State) did not bite**; the jsonschema dialect mcp-go uses does not mark
>   `omitempty` fields as required. If a future Go/Docker/mcp-go bump changes that, those tests go red first.
> - **Tests:** `internal/mcp/structured_result_test.go` (helper unit tests) and `internal/mcp/output_schema_test.go`
>   (schema advertised in `tools/list` + real output validates through dispatch). Added a reusable
>   `initMCPSession(t, handler)` helper there.
> - **Decision record:** the user chose "curated schemas + validation on" over "schemas everywhere" (too fragile for
>   huge Docker types) and "structuredContent only" (no enforcement). See the [progress log](#progress--deviation-log).

**The headline change.** Today every handler returns `(string, error)` and `registerTools` wraps it in
`NewToolResultText`. Switch to typed results so clients on `2025-06-18`+ receive `structuredContent`, while older
clients still get the text fallback.

**Changes:**

1. `internal/mcp/tools.go`: change `toolDef.handler` to `func(ctx, req) (any, error)`. In `registerTools`
   (lines 120-129), build the result with `mcplib.NewToolResultStructured(v, mustMarshalIndent(v))`. On handler
   error keep `NewToolResultError(err.Error())`.
2. New file `internal/mcp/results.go`: small result structs shared across handlers, each with JSON tags:
   - `ServiceMutationResult{ Service swarm.Service }` — scale, image, rollback, restart, all `update_service_*`.
   - `NodeMutationResult{ Node swarm.Node }` — availability, role, labels.
   - `RemovalResult{ Type, Name string; Removed bool }` — all `remove_*`.
   - `SearchResult` — wraps `cluster.SearchResults`.
   - `LogsResult{ Service string; Lines []LogLine }` — `get_logs`.
   - `TaskRemovalResult{ TaskID, ServiceName string; Removed bool }` — `remove_task`.
3. Attach `mcplib.WithOutputSchema[T]()` to each tool registration for its result type. Auto-derived from the struct
   — no hand-written schemas.
4. Handlers return the struct; the existing JSON shape becomes the text fallback, so REST/MCP parity is preserved.

**Acceptance:** a `tools/call` for `search` returns both a `content` text block and a `structuredContent` object
matching the advertised `outputSchema`. **Tests:** extend `tools_test.go` to assert `result.StructuredContent` is
non-nil and round-trips into the result type for one tool per result shape.

## Phase 2 — Server instructions + description

Give agents the usage contract up front.

**Changes:** `internal/mcp/server.go:125` — add to `NewMCPServer`:
- `mcpserver.WithInstructions(...)` — "Cetacean is a read-mostly Docker Swarm interface. Resolve IDs with the
  `search` tool before reads or writes. Reads are always available; mutations are gated by operations tier and ACL
  and may be hidden from `tools/list`. Prefer `cetacean://…` resources for detail; use tools to change state."
- `mcpserver.WithDescription("Read and safely operate a Docker Swarm cluster.")`.

**Acceptance:** `initialize` response carries `instructions` and `serverInfo.description`. **Tests:** assert both in
`server_test.go` / `integration_test.go` initialize assertions.

## Phase 3 — Tool icons (low priority, include for completeness)

`2025-11-25` lets tools/resources/server carry icons. Cosmetic but cheap and improves client rendering.

**Changes:** add a single SVG data-URI or hosted `https` icon to the server `Implementation` and, optionally, a
shared icon per tier. Keep it minimal — one server icon is enough to exercise the path.

**Acceptance:** icon appears in `serverInfo`. **Tests:** none beyond a presence assertion. *May be dropped if it
adds noise.*

## Phase 4 — Origin validation (403)

`2025-11-25` requires `403 Forbidden` for invalid `Origin` on streamable HTTP. mcp-go does **not** do this; add it in
our handler wrapper.

**Changes:** in `internal/mcp` Handler construction, wrap the streamable handler with an Origin check: when `Origin`
is present and not in the allowlist (reuse `CETACEAN_CORS_ORIGINS`; if unset, allow same-origin / no-Origin only),
return `403`. Non-browser agents send no `Origin` and are unaffected.

**Acceptance:** request with a foreign `Origin` gets `403`; no `Origin` or an allowed one passes. **Tests:** new
cases in `integration_test.go`.

## Phase 5 — OIDC Discovery 1.0 for the authorization server

`2025-11-25` enhances AS discovery with OpenID Connect Discovery. We already serve RFC 8414 metadata; add an
OIDC-compatible discovery document so stricter clients resolve the AS.

**Changes:** `internal/mcp/oauth/` — serve `GET {base}/.well-known/openid-configuration` returning a document that
overlaps our existing AS metadata (issuer, authorization/token/registration/revocation endpoints, `S256` PKCE,
`response_types_supported`, `grant_types_supported`, `token_endpoint_auth_methods_supported: ["none"]`). Reuse the
`asMetadata` builder; add only the OIDC-required fields we can honestly advertise. Add
`revocation_endpoint_auth_methods_supported` if not already present.

**Acceptance:** the OIDC discovery doc validates and points at the same endpoints as the RFC 8414 doc. **Tests:**
`oauth/server_test.go` (or a new `oidc_test.go`) asserts the document shape and endpoint consistency.

**This is the change that justifies bumping the CHANGELOG / `docs/mcp.md` authorization-profile reference from
`2025-06-18` to `2025-11-25`.**

## Phase 6 — Experimental tasks for long-running mutations (gated, reviewable)

> **Caveat — read before implementing.** The `2025-11-25` Tasks API is *experimental*. The `2026-07-28` RC reshapes
> it around statelessness (`tasks/list` removed, lifecycle changes). Implementing now means a migration later. mcp-go
> v0.54.0 supports it, which is why it's in this batch per the "implement what the library supports" decision — but
> if the migration cost outweighs the near-term value, convert this phase to a deferred issue instead.

Swarm mutations are asynchronous: `scale_service`, `update_service_image`, `update_node_availability` (drain),
`rollback_service`, and `restart_service` return immediately while reconciliation continues. Tasks let an agent poll
for convergence instead of guessing.

**Changes:**
- `internal/mcp/server.go`: `mcpserver.WithTaskCapabilities(true, true, true)` and a sane
  `WithMaxConcurrentTasks`.
- Register the five long-running mutations via `AddTaskTool`; the handler kicks the Docker write, then reports
  progress by polling the cache for desired-vs-running convergence until done/timeout/cancel.
- Keep the non-task variants too (a client that doesn't support tasks still calls the plain tool).

**Acceptance:** `scale_service` as a task returns a task handle; `tasks/get` reports progress and a terminal result
when replicas converge; `tasks/cancel` stops polling. **Tests:** a task round-trip in `integration_test.go`.

## Phase 7 — Validation-error conformance (confirm + lock in)

`2025-11-25` clarifies that input-validation errors should be Tool Execution Errors (`isError` result), not protocol
errors, so the model can self-correct. We are **already conformant** — handlers return `error`, which `registerTools`
converts to `NewToolResultError`. No code change; add a regression test.

**Acceptance/Test:** `tools_test.go` asserts that an invalid argument (e.g. `scale_service` with negative replicas,
empty `search` query) yields `result.IsError == true`, not a transport-level error.

## Deferred (tracked as issues)

Created on the repo; revisit when the `2026-07-28` spec finalizes and mcp-go ships support.

  the `initialize` handshake and `Mcp-Session-Id`; carry client info in `_meta`; explicit handle-passing. mcp-go's
  `WithStateLess` is only session-ID management, not this redesign.
- **Tasks lifecycle migration to 2026-07-28** — [#70](https://github.com/Radiergummi/cetacean/issues/70).
  `tasks/list` removed, stateless lifecycle. (Supersedes Phase 6 if/when that lands on the experimental API.)
- **MCP Apps — render Cetacean dashboards into agent clients** —
  [#71](https://github.com/Radiergummi/cetacean/issues/71). Server-rendered UI in sandboxed iframes over the audited
  JSON-RPC path.
- **OAuth hardening per 2026-07-28** — [#72](https://github.com/Radiergummi/cetacean/issues/72). RFC 9207 `iss`
  validation, OIDC `application_type` in DCR.
- **Missing-resource error code `-32002` → `-32602`** — [#73](https://github.com/Radiergummi/cetacean/issues/73).
  Library/spec-controlled; coordinate with the spec bump.
- **Durable OAuth/session store** — [#74](https://github.com/Radiergummi/cetacean/issues/74). Survive restarts (DCR
  registrations, refresh tokens, codes). The main v1 limitation; not spec-gated.
